  O que é

  É a etapa técnica de um processo seletivo da Contato Seguro, só de front-end.
  O back-end (PHP 8.4 + Slim 4 + Eloquent + Phinx) já está pronto em server/, e
  você implementa as telas em client/ (React 19, Ant Design 5, TypeScript,
  Dayjs, React Router 7, Vite).

  Regra principal: nada dentro de server/ pode ser criado, editado ou apagado. O
  server/AGENTS.md repete isso para agentes de IA, então eu também não vou
  mexer lá.

  O que o PRD pede

  O usuário é o membro de comitê, que recebe e investiga relatos.

  Épico 1: Pessoa
  - Cadastrar e listar pessoas, com nome, CPF, e-mail e data de nascimento
    (todos obrigatórios).
  - As pessoas são do sistema todo, não de uma empresa.
  - O CPF é único.
  - Cenários de validação: cadastrar e ver a pessoa na lista; tentar cadastrar
    um CPF repetido.

  Épico 2: Envolvimento
  - Vincular uma pessoa a um relato com um tipo: whistleblower (relatante),
    witness (testemunha), victim (vítima) ou denounced (denunciado).
  - Cada pessoa só pode aparecer uma vez por relato.
  - O relato é anônimo quando não tem nenhum relatante, e isso precisa ficar
    visível na tela.
  - Cenários de validação: criar um vínculo; ver um relato anônimo; testar um
    caso de falha.

  Contratos da API (http://localhost:8080)

  - /people: CRUD completo (GET lista e por id, POST, PUT, DELETE).
    - O CPF precisa ter exatamente 11 dígitos numéricos.
    - CPF repetido retorna 409.
  - /records/{record_id}/involvements: GET, POST ({ person_id, type }) e DELETE
    /{id}.
    - O GET devolve { involvements: [...com person aninhado], is_anonymous }. O
      back-end já calcula o anonimato.
    - Vínculo repetido retorna 409.
    - record_id ou person_id inválido retorna 404.
  - Todas as rotas estão em server/insomnia.json, que dá para importar no
    Insomnia.

  O que precisa ser entregue

  1. Um plano de design em Markdown (o que você entendeu, riscos e decisões).
  2. Um plano de implementação (opcional).
  3. A implementação em client/. Telas, indicadores e gráficos além do PRD
     contam como bônus.
  4. Um arquivo de evidências dos testes manuais. Para cada cenário: o que foi
     testado, como, o resultado esperado e o resultado obtido. Uma imagem por
     épico é bem-vinda.
  5. O Google Form de encerramento, que é obrigatório. Dá para anexar a conversa
     com o agente de IA.

  Como rodar

  docker compose up -d, depois dentro do container api: composer install,
  composer run phinx:migrate e composer run phinx:seed. A API sobe em
  http://localhost:8080 e o front em https://localhost:5100.

  relatos, rotas, cliente HTTP) antes de montarmos o plano de design?

  Esboço do docs/DESIGN_PLAN.md

  1. Entendimento do PRD
  - Pessoas valem para o sistema todo e o CPF é único.
  - Envolvimento liga uma pessoa a um relato com um tipo, e cada pessoa só
    aparece uma vez por relato.
  - O relato é anônimo quando não tem nenhum relatante. Quem calcula isso é o
    back-end, não o front.

  2. O que vai ser construído
  - Pessoas (/people, novo item no menu):
    - CRUD completo seguindo o padrão de Empresas.
    - CPF com máscara no campo e mascarado na tabela (***.456.789-**).
    - Busca por nome ou CPF.
    - Aviso ao excluir uma pessoa.
  - Relatos (/records):
    - Nova coluna Anônimo/Identificado, com uma chamada a /involvements por
      relato, feitas em paralelo.
    - Filtros por empresa, status e anonimato.
    - Link para a página de detalhe.
  - Detalhe do relato (/records/:id, rota nova):
    - Dados do relato e o selo de anonimato.
    - Tabela de envolvidos com remoção.
    - Modal "Vincular", com select de pessoa (busca por nome ou CPF), botão para
      cadastrar uma pessoa nova e select de tipo.

  3. Decisões
  - Não dá para editar o tipo de um envolvimento: para trocar, remove e vincula
    de novo.
  - As mensagens de erro da API serão traduzidas para PT-BR via makeMessage.
  - No select de vínculo, as pessoas que já estão no relato aparecem
    desabilitadas, para evitar o 409 antes do envio.
  - O código segue a mesma estrutura de domain/ que já existe (services,
    context, components).

  4. Riscos (documentados, sem testar)
  - O anonimato na listagem custa uma chamada por relato.
  - O soft delete com índice único pode dar 500 ao revincular uma pessoa ou
    recadastrar um CPF.
  - Vínculos de pessoas excluídas podem vir com person: null.
  - O back-end só valida o formato do CPF, não o dígito verificador.

  5. Fora do escopo
  - Testes unitários, por enquanto.
  - Qualquer mudança em server/.
